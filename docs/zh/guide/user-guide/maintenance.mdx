# 维护与故障排查

以下命令以 [Compose 部署](../getting-started/installation-guide/docker-compose)为例，在保存 `compose.yaml` 的部署目录执行。服务名为 `qinglong`，数据目录为 `./data`；其他部署方式请替换实际名称和路径。

## 升级前备份

备份应覆盖整个持久化数据目录，包括数据库、脚本、配置、日志以及已创建的 `script-history` 脚本历史目录。为避免复制正在写入的数据库，先停止面板，再打包：

```bash
docker compose stop qinglong
sudo tar -czf "qinglong-data-$(date +%Y%m%d-%H%M%S).tar.gz" data
docker compose start qinglong
```

确认打包成功后再继续升级。备份中可能包含账号信息、应用密钥和环境变量，应保存在受控位置。建议记录当前镜像版本或摘要，并将备份复制到独立存储。

## 升级镜像

本次版本沿用现有运行时：默认 Debian 镜像使用 Debian 12 与 Node.js 20；默认 Alpine 镜像通过 APK 安装 Node.js，两种默认镜像使用 Python 3.11。运行时迁移将在后续版本处理。具体配置见 [Docker 部署](../getting-started/installation-guide/docker)。面板内升级不会替换容器的系统、Node.js 或 Python；更换基础运行时需要拉取镜像并重新创建容器。

升级后先试运行具有代表性的 JavaScript、Python 和 Shell 任务，检查订阅及通知。用户安装的依赖不保证跨运行时兼容；出现原生模块加载错误、Python 扩展导入失败或缺失模块时，在新容器的依赖管理中重新安装对应依赖，并查看安装及任务日志。Python 3.10 已于 2026-10-01 [结束维护](https://devguide.python.org/versions/)，使用旧兼容镜像的用户应验证脚本在 Python 3.11 上的运行情况。

```bash
docker compose pull qinglong
docker compose up -d qinglong
docker compose logs --tail 100 qinglong
```

检查登录、脚本目录、任务和日志是否正常。需要固定版本时，将 `compose.yaml` 中的镜像改为所选的已发布标签或摘要后再更新。

不要将降级镜像视为完整回滚：新版可能改变数据结构。回滚时使用与备份相匹配的镜像和数据。

## 面板内升级

设置中的系统更新先下载并校验暂存产物，等待完成提示后，重载系统才会应用升级。API 的初始 `200` 只表示已启动后台准备；下载或校验结果通过 WebSocket 报告。也可在面板宿主机或容器内分两步执行：

```bash
ql update false
# 确认下载及校验成功后应用
ql reload system
```

准备阶段核对静态构建清单、文件哈希，以及清单所指定源码和锁文件的一致性；必要依赖在暂存目录安装，应用前再次校验。`stable`/`debian` 使用 `master` 来源，`develop`/`debian-dev` 使用 `develop` 来源。[内部工具](./local-cli)的 `update --download-only` 和 `reload --target system` 对应这两个步骤。

系统升级保留用户数据和 `.env`。程序替换失败或新服务未在约 60 秒的健康检查窗口内就绪时，尝试恢复旧程序并启动旧服务；这不会撤销已经发生的数据库或用户数据变更。升级前仍须完整备份。若恢复失败，保留剩余备份、暂存产物和升级日志，按备份处理，避免反复盲目执行更新。

## 恢复备份

停止面板，把当前 `data` 移到其他位置保留，再将备份解压到部署目录，使最终结构仍为 `./data/...`。确认文件所有者和权限符合运行用户要求后启动面板。不要直接把备份覆盖到正在运行的数据库上。

首次恢复建议在隔离环境中验证，并禁用定时任务或断开外部服务，避免恢复验证期间重复执行真实任务。

## 系统内部 API 令牌

青龙 2.23.0 修复了系统令牌未主动续期和认证缓存并发更新的问题。定时生成以及启动后重新计时会主动续期，避免长期运行后失效。面板内置 Shell API 在每次请求前检查令牌，遇到 401 时刷新并重试一次，其他错误不会自动重试。独立远程 CLI 使用配置的应用凭据或访问令牌，其认证排查见下表。

## 常见问题

| 现象 | 排查步骤 |
| --- | --- |
| 无法访问面板 | 执行 `docker compose ps` 和 `docker compose logs --tail 100 qinglong`，核对端口映射、`QlPort`、代理路径及防火墙 |
| 找不到脚本 | 核对脚本管理中的路径；子目录脚本使用 `task folder/hello.js` |
| 缺少 Node/Python 模块 | 在依赖管理中选择对应语言安装依赖，检查安装日志后再运行任务 |
| 定时未触发 | 检查任务是否启用、定时规则和时区；查看排队状态及运行中实例 |
| 挂载目录不可写 | 核对宿主机目录权限、容器运行用户和 SELinux 配置；非 root 部署参考 [Docker 说明](../getting-started/installation-guide/docker) |
| CLI 返回 401/403 | 检查凭据或令牌是否有效，使用 `ql auth status --scope crons --json` 检查目标模块；确认环境令牌没有覆盖已保存配置 |
| `ql` 不识别命令 | 用 `command -v ql`、`ql --help` 确认是[远程 CLI](./cli)还是[内部工具](./local-cli) |

`ql check` 会安装依赖、修复并重载服务；初步排查先查看日志和配置。日志分享前请移除 token、环境变量值和私有仓库凭据。

定时规则和时区边界见[任务 API](../../api/crontab)。使用夏令时的时区会跳过春季不存在的当地时间，秋季重复小时不执行第二次；`Asia/Shanghai` 不受夏令时影响。停机期间不提供持久化补跑保证；无效的已保存任务或订阅规则会跳过并记录诊断，配置仍保留供修正。
